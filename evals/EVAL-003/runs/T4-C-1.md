# Postmortem Review: checkout outage, 2026-09-18

## Adequately Supported Claims

**Claim 3 (Error rate peaked at 38%):** Supported by load balancer logs, a reliable source. Adequate.

**Claim 6 (Upstream DNS incident timing):** Verifiable from the DNS provider's status page. Adequate.

**Claim 7 (Alert would have fired at 14:06):** Supported by alert configuration and log replay. Adequate.

---

## Unsupported or Inadequately Supported Claims

**Claim 4 (Root cause is cache eviction in release 8.2):** MAJOR PROBLEM. The postmortem claims rollback of 8.2 caused the fix, but the evidence is weak:
- Rollback occurred at 14:50; outage ended at ~14:52 (2 minutes later)
- Upstream DNS provider's incident resolved at 14:49 (1 minute *before* rollback)
- No investigation described to rule out the DNS incident as the true cause or a contributing factor
- Temporal correlation between rollback and error cessation is not causation
- The postmortem does not explain why the DNS incident timing is coincidental

This conclusion jumps to blame the most recent code change without evidence that it caused the errors.

**Claim 5 (No customer data was affected):** UNSUPPORTED SCOPE. The verification was limited:
- Only "three services we suspected" were checked
- No systematic audit described across all services
- No definition of "checked" — were partial writes searched for, or assumed not to exist?
- No evidence that these three were the only possible affected services
- Conclusion goes beyond what spot-checking allows

**Claim 8 (This will not happen again):** ENTIRELY UNSUPPORTED. No evidence supports this absolute claim:
- If the root cause were truly the cache eviction, fixing it prevents *that specific bug*, not "this" (all future incidents)
- The postmortem did not rule out the DNS provider incident as a contributing cause; if DNS issues can cause this, it can happen again
- No architectural changes, circuit breakers, or process improvements are described
- No control is established (e.g., "we will not ship cache eviction changes without testing X")

This is a dangerously broad conclusion with zero supporting evidence.

**Claim 1 (Paged at 14:05):** Factually stated but inconsistent with Claim 2. If the outage started at 14:03, a 2-minute detection lag is noted but not explained. Minor issue, but suggests incomplete monitoring or alert tuning.

---

## Summary

**Well-supported:** Claims 3, 6, 7 (factual observations from logs and verifiable systems)

**Inadequately supported:** Claim 4 (correlation mistaken for causation; DNS incident not ruled out), Claim 5 (limited verification scope), Claim 8 (sweeping claim with no supporting evidence or preventive actions)

**Before publication:** The postmortem should
1. Investigate the DNS incident timeline and rule it in or out as a cause
2. Explain the verification process for Claim 5 and broaden the audit if needed
3. Replace Claim 8 with specific preventive actions (testing strategy, monitoring improvements, etc.) rather than a guarantee
