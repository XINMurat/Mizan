# Mizan Audit: Checkout Outage Postmortem (2026-09-18)

## Summary

This postmortem contains **one critical flaw and three supporting gaps** that must be resolved before publication. The stated root cause (release 8.2 cache eviction change) has a confounding variable (DNS provider outage) that the timeline evidence does not clearly separate. Two claims have internal arithmetic failures or scope-limited verification presented as comprehensive. The conclusion "this will not happen again" has no mechanism attached.

**Publishable as-is: No.**  
**Actionable findings that block publication:** 3 (causation confusion, data verification scope, prevention mechanism).

---

## Audit by Claim

### 1. "The on-call engineer was paged at 14:05"
- **Tag:** `[H]` Makul Hipotez / Plausible hypothesis
- **Reasoning:** No evidence source provided. Pager logs would verify this; without them, time is stated but unconfirmed.
- **Source needed:** Alert system or pager dispatch logs.

---

### 2. "The outage lasted 47 minutes, from 14:03 to 14:52"
- **Tag:** `[R]` Reddedildi / Refuted (internal contradiction)
- **Reasoning:** Arithmetic failure: 14:03 to 14:52 is 49 minutes, not 47. This is not a typo; it is a measurement claim that does not survive its own numbers. Additionally, claim 1 states paging occurred at 14:05, which is **2 minutes after the outage allegedly began** — no detection lag is plausible for a 38% error rate (claim 3). One of these times is wrong.
- **Mechanism of error:** Either the outage start time is incorrect, the page time is incorrect, or both. The postmortem does not say which.
- **Next step (criticality: HIGH):** Reconstruct the timeline from load balancer logs, pager dispatch logs, and release logs. A 2-minute gap between outage onset and detection is either unexplained delay (finding) or a wrong timestamp (correction required).

---

### 3. "Error rate peaked at 38% of requests (load balancer logs)"
- **Tag:** `[K]` Kanıtlanmış / Proven
- **Reasoning:** Specific measurement with identified source (load balancer logs). Verifiable if logs are accessible.
- **Note:** The claim is about the peak, not the duration at peak; specificity preserved.

---

### 4. "Root cause: the cache eviction change shipped in release 8.2. We rolled 8.2 back at 14:50 and errors stopped shortly after."
- **Tag:** `[KKE]` Kritik Kontrol Eksik / Critical control missing
- **Reasoning:** This claim contains a **confound that is explicitly documented elsewhere in the postmortem**. Claim 6 states that the upstream DNS provider experienced an incident resolved at 14:49. The timeline is:
  - DNS incident resolved: 14:49
  - Release 8.2 rolled back: 14:50
  - Errors stopped: "shortly after" (≤ 14:52)

  If DNS recovered at 14:49 and errors stopped shortly after 14:50, the causation is ambiguous. The postmortem asserts cache eviction caused it, but **does not distinguish between (a) the rollback fixed it, (b) DNS recovery fixed it, (c) both contributed, or (d) DNS recovery happened to coincide with an independent metric improvement.**

  Two specific controls are missing:
  - **Negative control:** Did errors stop at 14:49 (when DNS recovered) or only after 14:50 (after rollback)? The load balancer logs will show error rate per minute. This will either confirm the rollback or reveal that DNS recovery alone ended the incident.
  - **Code mechanism:** What in the cache eviction change could cause a 38% error rate? No log sample, stack trace, or symptom pattern is provided. Without this, the causation chain is: outage → release 8.2 in production → assume it was the thing we just shipped. (This is not diagnostic rigor; it is post-hoc convenience.)

- **Next step (criticality: CRITICAL):** Separate the two incidents. (1) Plot error rate minute-by-minute against DNS status and rollback timestamp in the same timeline. If error rate fell at 14:49 (DNS recovery), DNS was the cause and release 8.2 is unrelated. If it fell only at 14:50+ (post-rollback), cache eviction is plausible. If both coincided, you cannot tell. (2) Reproduce the cache eviction bug in staging using the 8.2 code path and request patterns from the incident. (3) Check whether release 8.2 was canary-deployed or went to 100% of the fleet at once; if gradual, the error curve slope might reveal the causation.

---

### 5. "No customer data was affected: we checked the three services we suspected might have written partial orders."
- **Tag:** `[Y]` Yanıltıcı / Misleading
- **Reasoning:** The claim's framing ("no customer data was affected") is broader than its evidence ("we checked three services"). The postmortem does not say (a) how many services *could* have written partial orders, (b) why these three were the only suspects, or (c) what "checked" means (query for orphans? byte-level integrity? transaction logs?). If a fourth service wrote corrupted state and nobody suspected it, the claim is false and the postmortem will have published a false all-clear. The technically true statement — "we checked three services" — is presented as the reassuring conclusion "no data affected" without stating the verification scope.

- **Next step (criticality: HIGH):** (1) List all services that touched the checkout flow during 14:03–14:52. (2) For each, state whether it was verified and if so, how (log search, data query, integrity check, transaction audit). (3) For any unverified service, explain why it could not have written partial data (e.g., it is read-only, it has no writes, it was not in the request path).

### 6. "The upstream DNS provider's status page records an incident on their side, resolved at 14:49."
- **Tag:** `[K]` Kanıtlanmış / Proven
- **Reasoning:** External, time-stamped, publicly documented. Verifiable by visiting the status page.
- **Critical note:** This is not a supporting detail; it is a confounding variable that the postmortem fails to isolate from claim 4. See claim 4 audit.

### 7. "We added an alert that fires when the error rate exceeds 5% for 2 minutes; replayed against this incident's logs, it fires at 14:06."
- **Tag:** `[K]` Kanıtlanmış / Proven
- **Reasoning:** The alert rule and replay test are verifiable if the alert code and logs are accessible. Replay validation is a strong control.
- **Tension with timeline:** This alert would have fired at 14:06, but claim 1 says paging was at 14:05. This is a one-minute gap in the claimed detection time. Either the pager response was faster than the new alert would have been, or the "paging at 14:05" is retroactively filled in. This is a minor point but adds to timeline instability.

---

### 8. "This will not happen again."
- **Tag:** `[S]` Spekülatif / Speculative
- **Reasoning:** No mechanism is provided. Does "this" mean (a) cache eviction bugs will not ship, (b) DNS outages will not happen, (c) we will detect any outage within 1 minute, or (d) all three? The alert (claim 7) may prevent undetected outages, but it does not prevent the release 8.2 cache eviction bug from being shipped to production again if the testing process that missed it is unchanged. A conclusion with no supporting mechanism is a prediction, not a justified claim.

- **Next step (criticality: MEDIUM):** State explicitly: which future event does the alert prevent, which does the reviewed release process prevent, and which risk remains unmitigated. Separate the mechanisms.

## Missing Information (Cannot Be Verified From Postmortem)

**Format-level omissions** — what the incident-postmortem genre structurally does not show, but should be present for publication:

1. **Confound separation.** Two concurrent failures (release 8.2, DNS outage) are presented as one root cause. The postmortem must show that the timeline of error recovery matches the rollback, not the DNS recovery.

2. **Verification scope on data integrity.** "No customer data affected" is asserted based on sampling three services. The postmortem must list all services in scope and state which were and were not verified, and why.

3. **Prevention mechanism.** The alert prevents future *undetected* outages, not future *cache-eviction* outages. These are different claims. The postmortem must separate them.

4. **Root cause confirmation by code.** Why did the cache eviction change cause a 38% error rate? A stack trace, error log snippet, or statement of the mechanism is missing. Correlation (release shipped, outage happened) is not diagnosis.

5. **Detection gap.** Outage allegedly began at 14:03; paging at 14:05. Why did the alert not fire at 14:03 (claim 7 says it would fire by 14:06, implying near-instant detection)? Is the paging time wrong, or was there a 2-minute delay in error visibility to the alert system?

## Recommendations (Criticality Order)

### CRITICAL — Must resolve before publication:
1. **Separate DNS and release 8.2 causation.** Plot error rate against DNS status and rollback time. If error rate fell at DNS recovery (14:49) and stayed low through rollback (14:50), DNS was the cause and release 8.2 is unrelated. If it fell only after rollback, the rollback is the candidate cause — but still unproven without mechanism.  
   *Cost if wrong:* Publication of incorrect root cause; identical bug will ship again; DNS outages will be blamed on unrelated deployments.  
   *Cost if not fixed:* None yet, but high risk.

2. **Verify the timeline arithmetic.** 14:03 to 14:52 is 49 minutes, not 47. Confirm which time is correct: start, end, or duration. Reconcile the 2-minute gap between outage onset (14:03) and paging (14:05).  
   *Cost if wrong:* Detection delay will be hidden and detection process will not be fixed.  
   *Cost if not fixed:* Future outages with similar delays will recur.

3. **List and verify all checkout services for data corruption.** The postmortem verified three services the team suspected. You cannot verify services you did not think to check. Either audit all services in the checkout path or publish a scope statement ("verified: order, payment, shipping; unverified: inventory, coupon, fraud-check").  
   *Cost if wrong:* Silent data corruption in an unverified service; customer data loss discovered weeks later.  
   *Cost if not fixed:* Medium risk; incident response usually finds corruption within 48 hours, but that is reactive, not preventive.

### HIGH — Should resolve before publication:
4. **State the prevention mechanism for "this will not happen again."** Explicitly list what will be prevented (cache-eviction bugs, undetected outages, simultaneous DNS/deploy coincidences) and what will not (general provider outages, unknown unknowns). Separate the alert's role from the release process's role.

### MEDIUM — Can resolve post-publication if necessary:
5. **Provide code evidence for cache eviction causation.** A stack trace, slow-query log, or memory-dump from the incident (if available) would confirm the mechanism. If the incident logs do not contain this, retrospective reproduction in staging using 8.2's code and the incident's request log will.

## Tone Note

The postmortem reads as written in good faith and thorough in some areas (alert validation, external status pages). The gaps are not malice; they are structural: a simultaneous external outage (DNS) created a natural confound that was not separated, and verification scope was not formally stated. These are exactly the failure modes Mizan's step-by-step process is designed to surface.
