# Review: Checkout outage postmortem (2026-09-18)

## Summary
The postmortem mixes things that are checkable with conclusions it has not earned. It has one arithmetic error (#2). Its central causal claim (#4) has a competing explanation in the document itself (#6). Its data-safety claim (#5) goes further than the check it describes. And #8 is a promise, not a finding. **Do not publish it as written.**

## Claim-by-claim

| # | Claim | Verdict | Notes |
|---|---|---|---|
| 1 | Paged at 14:05 | Plausible, no source given | Cite the paging system record. It fits an outage start of 14:03. |
| 2 | Lasted 47 min, 14:03–14:52 | **Internally inconsistent** | 14:03 to 14:52 is **49 minutes**. Either the duration or one of the timestamps is wrong. Also say how start and end were defined, for example the first and last minute above some error threshold. |
| 3 | Peak error rate 38% (LB logs) | Supported, with a source | This is the best-sourced claim. Add the time of the peak and the measurement window. |
| 4 | Root cause: cache eviction change in 8.2. Rollback at 14:50 and errors stopped | **Not established. Confounded** | The only evidence is timing: errors stopped after the rollback. But #6 says the DNS provider's incident was resolved at 14:49, one minute *before* the rollback. That is an equally good or better fit for recovery at about 14:52. The document offers no mechanism linking the eviction change to checkout errors. It also does not say when 8.2 was deployed relative to 14:03. A deploy long before the outage would weaken the claim. |
| 5 | No customer data affected | **Overclaimed** | The check covered only "the three services we suspected." The search was limited to what was already suspected, so it cannot support "no data affected." Supported version: "No partial orders were found in services A, B and C." Also say what was checked (which tables, and how partial orders were detected). Either check the remaining services that write data or state the limit. |
| 6 | DNS provider incident resolved 14:49 | Supported (external status page), but **ignored** | The report records this fact and never deals with it. When did the DNS incident start? If it started around 14:03, DNS becomes the leading explanation. |
| 7 | New alert (>5% for 2 min) would fire at 14:06 on replay | Supported as a replay result | This is fine, but note that it fires *later* than the actual page (14:05), so it does not improve detection for this incident. Say what the alert is for, and check how often it would fire falsely on normal traffic. |
| 8 | "This will not happen again" | **Unsupported / unfalsifiable** | Remove it. Replace it with specific remediation items, each with an owner and a date. |
| 9 | Retrospective held Friday | Fine (process fact) | Add the date. It was presumably 2026-09-25 or 2026-09-19. |

## What is supported
- #3 (peak error rate, from logs), #6 (DNS incident resolution time, from an external source), and #7 (replay result). #1 and #9 are plausible facts that should be given a source or a date.

## What is not supported
- **#4, the root cause:** timing only, and confounded by DNS recovery one minute earlier.
- **#5, no data impact:** only the suspected services were checked.
- **#8:** a promise, not a conclusion.
- **#2:** the arithmetic is wrong. Fix it before publishing.

## Required before publishing
1. Correct the duration or the timestamps in #2.
2. Separate the two explanations. Get the DNS incident's start time. Check whether the failed requests were DNS resolution failures (error types in the LB logs). Check whether 8.2's deploy time lines up with 14:03. The strongest test is to re-deploy 8.2, or its eviction change, in staging or as a canary with DNS healthy. If errors come back, the root cause holds. If not, it is refuted. Until then, change the wording to "suspected contributing cause."
3. Reword #5 to match its scope, or widen the check to every service that writes orders.
4. Replace #8 with tracked action items.
5. Write down the limits of the new alert. It would not have caught this incident any earlier than the actual page did.
