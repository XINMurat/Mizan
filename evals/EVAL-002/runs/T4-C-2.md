# Review: Checkout outage postmortem (2026-09-18)

**Verdict:** Do not publish yet. The timeline facts mostly hold up. The main conclusion, the root cause, does not. The postmortem's own evidence (claim 6) gives an equally good alternative explanation, and the document never addresses it.

## Claim by claim

**1. Paged at 14:05.** Supported, assuming it comes from the paging system's record. Cite the source, such as the PagerDuty or Opsgenie log.

**2. Outage lasted 47 minutes, 14:03 to 14:52.** The numbers don't match. 14:03 to 14:52 is **49 minutes**, not 47. Either a timestamp or the duration is wrong. The document also doesn't say how start and end were defined (what error-rate threshold, from which source). Fix this and state the definition.

**3. Error rate peaked at 38% (load balancer logs).** Mostly supported: it has a named, objective source. Caveats:
- Say what counts as an error (5xx only? timeouts?) and over what window the 38% was measured.
- Load balancer logs don't capture requests that failed before reaching the LB. If DNS was involved (claim 6), those failures would be missing, so the real impact could be higher.

**4. Root cause: cache eviction change in release 8.2.** **Not supported as written.** This is the central problem.
- The only evidence is timing: rollback at 14:50, errors stopped "shortly after" (14:52).
- Claim 6 says the upstream DNS provider's incident was resolved at **14:49**, one minute *before* the rollback. Recovery at 14:52 fits the DNS fix at least as well as the rollback, and DNS TTL propagation could easily explain a ~3-minute lag.
- The two explanations can't be told apart from this data. Recovery after a rollback is not proof of cause when another fix landed in the same window.
- Nothing is offered about the mechanism: how the eviction change would produce checkout errors, and whether the errors looked like cache failures (cache misses, backend overload) or like DNS failures (resolution errors, connection failures).
- There's no baseline or control either. When did 8.2 deploy relative to 14:03? When did the DNS incident start relative to 14:03? Did services not using the 8.2 cache path also fail?
- What would settle it: compare error types in the logs, line up both incidents' start times, try reproducing the eviction behavior in staging, and check whether 8.2 was ever redeployed without errors recurring.
- Suggested rewording: "Suspected contributors: release 8.2 cache eviction change and/or upstream DNS incident; root cause not yet confirmed."

**5. No customer data affected.** **Not supported. The conclusion goes further than the evidence.** Checking only the three services the team *suspected* is not the same as checking everything that could be affected. Absence of evidence in a pre-selected subset doesn't show absence everywhere. Also missing:
- how those services were checked
- which other services touch orders, payments or inventory
- whether payments were captured without orders being created
- whether any customers complained or opened support tickets

At most it supports: "no partial orders found in services A, B and C."

**6. DNS provider's status page records an incident, resolved at 14:49.** Supported as a fact about the status page. Link it and record when their incident started. It is well supported, and it directly undermines claim 4. The postmortem mentions it and then ignores it.

**7. New alert (>5% for 2 min) would have fired at 14:06 in replay.** The replay itself is reasonable evidence that the alert works on this incident. The conclusion it implies doesn't follow:
- The engineer was already paged at **14:05**, so the new alert would have fired a minute *later* than the existing paging. It adds no detection speed for this incident, so its value needs to be justified some other way.
- The threshold was tuned on the same incident it was tested against, which is circular. Test it against other incidents and normal traffic to check its false-positive rate.

**8. "This will not happen again."** **Not supported and can't be.** The root cause isn't established (claim 4). The only remediation listed is an alert, which detects problems and does not prevent them. Nothing addresses DNS dependency or resilience. Replace it with specific, trackable action items (owner, due date) and a realistic statement of what the risk reduction is.

**9. Retrospective held on Friday.** Probably true but uninformative. Give the date and link the notes and action items. It isn't evidence for any conclusion.

## Required before publishing
1. Fix the duration arithmetic and define outage start and end.
2. Put 8.2 and DNS side by side as candidate causes, using error-type and timing evidence. Downgrade to "suspected" until one is confirmed.
3. Widen the data-integrity check beyond the three suspected services, or narrow the claim.
4. Re-justify the alert given the 14:05 page, and validate it on other data.
5. Replace claim 8 with concrete action items, including DNS resilience.
