# Review of PR #482: faster config parser

**Verdict: not ready to merge.** One claim holds up well (6). One is partly supported (5). Claims 1 and 4 are weak. Claim 2 has no valid evidence behind it, and the PR's own description contradicts claim 3.

## 1. "All tests pass": overstated
- **Evidence:** CI reports 214 passed and 3 skipped.
- **Problem:** "Skipped" does not mean "passed." All three skipped tests are in `test_parser_legacy.py`, which covers the legacy parser, the exact code this PR replaces. So the skips may be hiding the regressions that matter most. Did this PR cause the skips, or did they exist before? Nobody has said.
- **Needed:** Say why the tests are skipped and whether this PR introduced the skips. Then unskip them, or show they were already skipped on main for an unrelated reason and still pass against the new parser.
- **Accurate wording:** "214 passed, 3 legacy-parser tests skipped."

## 2. "Parsing is 40% faster": unsupported
- **Evidence:** One run on the author's laptop, compared with last month's production dashboard latency.
- **The comparison is invalid:**
  - **Hardware and environment:** a laptop versus production servers.
  - **Workload:** unknown laptop inputs versus real production configs.
  - **What was measured:** dashboard latency probably covers end-to-end request time (I/O, network, other code), not parser time alone.
  - **Timing:** the numbers come from different periods, and other changes happened in between.
- **No valid baseline:** the old parser was never run on the same machine with the same inputs. No control.
- **One run:** a single measurement shows nothing about variance or noise, has no confidence interval and no warm-up. Laptop turbo boost, thermal throttling and background load can easily move results by 40%.
- **Who judged:** the author alone. There is no reproducible benchmark script.
- **Needed:** An A/B micro-benchmark on the same machine, running old and new parsers on the same representative configs, repeated many times, reporting the median and spread. Commit the benchmark script so others can reproduce it. Until then, drop the "40%" figure.

## 3. "No behaviour change": contradicted by the diff
- The PR changes the default of `strict_mode` from `true` to `false`. That is a behaviour change by definition. It is also a risky one: configs that used to be rejected may now be accepted, with typos, unknown keys or bad values silently ignored or coerced. That affects correctness, and possibly security.
- **Needed:** Take the default change out of this PR, or declare it openly as a breaking or behavioural change, with a reason, a changelog entry and a migration note. Also add tests that show which inputs strict mode handled differently.

## 4. "Security reviewed": not an independent review
- **Evidence:** The author read through their own input handling and "it looks fine."
- **Problems:**
  - The author reviewed their own work.
  - There is no stated method, checklist or threat model.

- **Needed:** A review by someone other than the author. Tests for hostile inputs: deeply nested structures, huge files, bad encodings, injection through values, and unknown keys under non-strict mode. Ideally, run a fuzzer for a while.
