# Claim review: SparseRoute

## Headline claim
"SparseRoute improves BenchQA accuracy from 71.2 to 74.8, a significant improvement over the prior state of the art."

**Verdict: Not supported as stated.** Only the claim that one run reached 74.8 on the test split, under test-tuned hyperparameters, is supported. The rest breaks down into four parts:

| Sub-claim | Status | Why |
|---|---|---|
| SparseRoute scores 74.8 | Weakly supported (a single observation) | One training run (note 1), so there is no variance estimate. Hyperparameters were grid-searched on the test split (note 2). That is test-set leakage, so 74.8 is an optimistically biased estimate and does not show how well the method generalizes. |
| Baseline is 71.2 | Unverified for comparison purposes | The number was copied from a 2019 paper and the baseline was not re-run (note 3). Differences in data version, preprocessing, eval script, compute budget and tuning effort are not controlled. The baseline also had no test-set tuning advantage, so the comparison is asymmetric. |
| +3.6 points is an "improvement" caused by the method | Not supported | The gap mixes the method effect with test-set tuning, run-to-run noise and a pipeline mismatch. None of these is separated out. |
| "Significant" | Unsupported | No statistical test was run (note 4) and n=1, so no test was even possible. The word should be removed or clearly marked as informal. |
| "Prior state of the art" | Unsupported | The only comparison is a 2019 baseline. Nothing shows it was still SOTA at submission time. |

## What is supported
- **The ablation (note 5): the routing gate contributes about 2.1 points within this setup.** This is the best-evidenced claim. It is a controlled comparison: same seeds, data and budget, 3 seeds per arm, std 0.3. A 2.1-point gap against std 0.3 is large relative to the noise. Caveats:
  - 3 seeds is few.
  - Whether the gate evaluation used test-tuned hyperparameters is not stated. If it did, the absolute numbers are inflated, although the relative gap is less affected.
  - This shows the gate matters *inside SparseRoute*. It does not show that SparseRoute beats the baseline.
  - The seeded ablation also contradicts note 1 ("all numbers from a single run"). The authors should reconcile the two.
- **Reproducibility (note 6):** Releasing the code, configs, eval script and per-table commits is a real strength. It supports "the results can be checked", but it does not make them valid.

## Needed to support the headline
1. Re-select hyperparameters on a validation split and report the test score once.
2. Run multiple seeds (for example 5 or more) and report mean ± std or CIs.
3. Re-run the baseline in the same pipeline with the same tuning budget.
4. Run an appropriate significance test (for example a paired bootstrap over test items plus a comparison across seeds), or drop "significant".
5. Compare against current SOTA, not only the 2019 baseline, or drop the SOTA claim.

## Bottom line
The abstract's main claim, a significant SOTA improvement from 71.2 to 74.8, is not supported: it rests on a single run, test-set tuning, an unreplicated baseline and no statistical test. The ablation is the one claim with credible support. Code release makes these problems checkable, but it does not fix them.

# Review of SparseRoute claims

## Headline claim: 71.2 -> 74.8 on BenchQA, "significant improvement over prior SOTA"

**Not supported.** The methods note undermines it in four independent ways, and each one is enough on its own to block the claim.

1. **Single run (note 1).** 74.8 is one sample. We have no variance estimate for the full model. The ablation reports a std of 0.3 across seeds, which suggests seed noise may be small. But that std comes from a different configuration, and it cannot stand in for a variance measured on the headline number.
2. **Test-set tuning (note 2).** The learning rate and routing temperature were grid-searched on the BenchQA *test* split. That leaks test information into model selection, so 74.8 is an optimistically biased best-of-grid number and not a held-out estimate. This is the most serious flaw. The number cannot be read as generalization performance until it is re-tuned on a validation split and evaluated once on test.
3. **Stale, non-reproduced baseline (note 3).** 71.2 was copied from a 2019 paper and never re-run. The two systems likely differ in compute budget, data preprocessing, eval script, tuning effort and hardware or library versions. We also don't know whether the 2019 baseline was tuned on test. With no controlled baseline, the 3.6-point gap can't be attributed to SparseRoute. "Prior state of the art" is also doubtful: a 2019 number is unlikely to be the SOTA as of this paper, and no newer methods are compared.
4. **"Significant" without a test (note 4).** No statistical test was run, so the word "significant" has no basis. It should be removed, or backed by a real test (multiple seeds for both systems, CIs, or a paired bootstrap over test items).

Who judged the result: the authors did, on a split they also used for tuning. Nobody did an independent or blinded evaluation.

## Ablation claim: the routing gate contributes ~2.1 points

**Largely supported, with limits.** This is the best-designed evidence in the paper:
- It is a controlled comparison: same seeds, data and budget.
- It uses 3 seeds per arm with std 0.3, so a 2.1-point gap is about 7 std. A difference that large is very unlikely to be seed noise, although n=3 is small and no formal test is reported.

Caveats:
- If the ablation is also evaluated on the test split with hyperparameters tuned on test (note 2), both arms share that bias. The full model's hyperparameters, including the routing temperature, were tuned *for the gated model*, so the no-gate arm may be under-tuned and the gap inflated.
- The claim only covers the gate's contribution *within this setup*. It says nothing about superiority over the baseline.
- The ablation's full-model arm (3 seeds) is not the same as the single-run 74.8 in the abstract. The paper should report its mean and reconcile the two numbers.

## Reproducibility claim: code, configs, eval script and exact commits released

**Supported as a claim about artifacts** (note 6), assuming the repository actually exists and contains what is described. This is a real strength, because it lets others check everything above. It does not fix the flaws themselves: releasing the code for a test-tuned, single-run result still gives you a test-tuned, single-run result.

## Summary

| Claim | Verdict | Key problem |
|---|---|---|
| 74.8 accuracy | Not supported as an unbiased estimate | Single run; hyperparameters tuned on test |
| Improvement over 71.2 baseline | Not supported | Baseline copied from 2019, not re-run, no controlled comparison |
| "Significant" | Not supported | No statistical test was run |
| "Prior state of the art" | Not supported | Stale 2019 reference, no recent comparisons |
| Routing gate helps (~2.1 pts) | Mostly supported | Controlled, multi-seed; possible tuning asymmetry and test-split use |
| Code/configs/commits released | Supported (verifiable) | Enables reproduction, doesn't fix the design |

## What would fix it
- Re-tune on a validation split and evaluate on test once.
- Re-run the baseline in the same codebase with the same budget and tuning effort.
- Report both systems over 3 or more seeds as mean ± std, and use a paired significance test or bootstrap CIs.
- Compare against current SOTA methods, not only a 2019 baseline.
- Tune the no-gate ablation arm separately.
- Drop "significant" and "state of the art" unless the new evidence supports them.
