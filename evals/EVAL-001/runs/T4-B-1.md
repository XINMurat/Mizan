# Mizan Audit — PR #482 "faster config parser"

**Mode:** Audit (retrospective), code-flavored (Mode 3 hop audit) + Mode 5 gate for the merge decision.
**HARKing status:** Retrospective. The PR author chose which evidence to present after seeing results; this audit is also retrospective and was performed on the PR description only.
**Coverage statement:** 6 top-level claims atomized into 13 checkable sub-claims. 0 of 13 verified against primary artifacts — I had no access to the diff, CI run, coverage report, staging logs, or benchmark script. Every tier below is based on the *internal consistency of the description itself*. Several claims are refuted or downgraded purely from what the description says; none can be promoted to `[K]` without opening the attachments. Domain probe (step 7) not performed: no domain owner supplied scenarios (`supplied_by: none`).

**Verdict: Do not merge as-is.** One claim is self-contradicted in the description itself (#3), two are misleading framings (#1, #2), one is author-arbitrated and capped at `[KKE]` (#4), and the remaining two are plausible but unverified and depend on #3.

## Claim-by-claim

### 1. "All tests pass."
- 1a. "214 passed" — `[H]` Makul Hipotez / Plausible. CI summary quoted, not linked; also R25: which commit did CI run against? Check the CI run's SHA equals the PR head.
- 1b. "All tests pass" — **`[Y]` Yanıltıcı / Misleading.** 3 tests were skipped, and not random ones: all of `test_parser_legacy.py`, i.e. exactly the tests for the component this PR rewrites. A skipped test is silence, not a pass. "All" should read "214 of 217 ran and passed; the legacy parser suite was skipped."
- **Required:** state why the legacy tests are skipped (pre-existing skip or added in this PR?). If added in this PR, this is the most important finding in the review — the tests most likely to catch a behaviour change were turned off in the same change that claims no behaviour change.

### 2. "Parsing is 40% faster."
- **`[Y]` Yanıltıcı / Misleading — and methodologically `[R]`-grade as a measurement.**
- Mechanism of error: the comparison is **new code on a laptop, n=1** vs **old code in production, last month's dashboard**. Hardware, load, input distribution, network, time period and measurement instrument all differ. The 40% is a difference between two environments, not between two parsers. It cannot be attributed to the change at all.
- Also: a single run has no variance estimate; 40% is inside what environment noise alone can produce.
- Surprising-positive rule: a flattering 40% needs a symmetric control before it becomes a headline.
- **Required (preregister before rerunning):** same machine, same input corpus (sample of real configs), old vs new build, interleaved, n ≥ 30 runs per arm, report median and p95 with spread. Threshold stated in advance (e.g. median speedup ≥ 20% with non-overlapping IQRs). Kill condition: < 5% or within noise → drop the performance claim from the PR, keep only if other justification exists.

### 3. "No behaviour change."
- **`[R]` Reddedildi / Refuted — by the PR's own parenthetical.** Changing the default of `strict_mode` from `true` to `false` *is* a behaviour change, by definition: every caller relying on the default now gets different behaviour. The claim and the counter-evidence sit in the same line.
- Impact is likely non-trivial: strict mode typically rejects malformed/unknown keys. Flipping it to lenient means config that used to fail loudly may now be silently accepted — typos in keys ignored, bad values coerced. This is also a **security/safety-relevant** change (see #4).
- Conjunction (step 8): `strict_mode=false` × "skipped legacy tests" × "backward compatible" — the three together mean the most likely regressions would be invisible to both the test suite and the staging check.
- **Required:** either revert the default (and split it into a separate PR with its own justification, changelog entry and migration note), or retract "no behaviour change" and document the change explicitly.

### 4. "Security reviewed."
- **`[KKE]` Kritik Kontrol Eksik / Critical control missing — permanent under current arbiter.** Arbiter is `author` (self-review of own code). An author-arbitrated claim cannot reach `[K]`. "Looks fine" has no threshold, no scope, no named checks.
- Additionally the framing is `[Y]`-adjacent: "security reviewed" suggests an independent review happened.
- Not exploited / nothing found is not a pass (Mode 7, R26).
- A parser is a trust boundary: it consumes input. Relevant classes an independent reviewer should check: malformed/oversized input (DoS, deep nesting, huge values), injection via interpolation/includes, path traversal if the format supports includes, type confusion — and specifically the effect of `strict_mode=false` on what unvalidated input now reaches the app.
- **Required:** independent reviewer (not the author), with the checklist above; fuzz the new parser branches (e.g. a few minutes of property/fuzz testing against old parser as oracle on valid inputs).

### 5. "Added 12 unit tests; branch coverage 81% → 88%."
- 5a. 12 tests added — `[H]`; checkable in the diff, not checked here.
- 5b. Coverage 81 → 88% — `[H]`; attached report not seen. Note the confound: skipping `test_parser_legacy.py` changes the denominator/numerator too; confirm both numbers were computed on the same file set.
- 5c. Implicit claim "these tests cover the new branches adequately" — `[H]`. Coverage measures execution, not assertion. Check that the tests assert on outputs, and that there are tests for the `strict_mode` default (there apparently are none that failed, which is itself informative: either the default is untested, or tests set it explicitly).
- Credit where due: this is the best-evidenced claim in the PR — specific, numeric, with an artifact attached.

### 6. "Backward compatible: client v3.2 vs new server, 200 requests, 0 errors."
- `[H]` Makul Hipotez / Plausible, with `[KKE]` on the scope.
- Credit: real test, real artifact, numeric result.
- Limits: (a) one client version — are older supported clients (v3.0, v3.1…) in scope? (b) 200 requests: 0 errors bounds the error rate only to roughly < 1.5% (rule of three: 3/200) at 95% confidence — weak for a parser handling every request. (c) "0 errors" measures crashes/HTTP errors, not *semantic* compatibility: with `strict_mode=false`, the likely failure mode is silent acceptance of what used to be rejected, which returns 200 and produces no error. The check is structurally blind to the main risk of claim #3. (d) Were the 200 requests representative (real configs, including malformed ones) or synthetic happy-path?
- **Required:** replay a sample of real production configs through old and new parser and diff the parsed results (differential test); include known-invalid configs and assert they are still rejected.

## Missing card
A PR description structurally shows what was done and what passed. It does not show: what was *not* tested (skipped suite, other client versions, invalid inputs), what changed besides the headline (the default flip appears only as a parenthetical), and the rollback plan. Sketch from available evidence: untested = legacy parser behaviour, lenient-mode semantics, older clients, adversarial input; rollback = none stated.

## Mechanism, not motive
The pattern (headline claims stated flatly, contradicting details in parentheses) is typical of PR templates that reward checkbox claims. No intent is implied; the author disclosed the skip and the default change, which is to their credit — the problem is that the summary claims were not updated to match the disclosed facts.

## Next steps (ordered by criticality × impact/effort)
1. **Resolve `strict_mode`** (critical, low effort): revert the default, or split into its own PR with changelog/migration note. Retract "no behaviour change" otherwise.
2. **Explain and un-skip `test_parser_legacy.py`** (critical, low effort): if skipped in this PR, un-skip and fix or justify each test.
3. **Differential test old vs new parser** on real configs incl. invalid ones (high, medium effort): this is the real evidence for #3 and #6.
4. **Independent security review + short fuzz run** (high, medium effort): replaces the author-arbitrated claim.
5. **Redo the benchmark like-for-like** with the preregistered design in #2 (medium, low effort) — or drop the number from the PR.
6. Verify CI SHA = PR head, and coverage computed on the same file set (low effort).

## Merge gate (preregistered, for the re-review)
- Merge if: `strict_mode` default unchanged or explicitly documented; legacy suite runs and passes; differential test shows 0 unexplained diffs on ≥ 1,000 real configs; independent security sign-off recorded.
- Performance claim kept in the PR only if the like-for-like benchmark meets its preregistered threshold.
- Kill/hold condition: any unexplained differential diff, or legacy tests failing when un-skipped.
- Arbiter: CI runtime (tests, differential test), benchmark instrument (perf), named third-party reviewer (security). Author is not an arbiter for any gate item.

**Recommendation on continuity:** since this is a living repo, the recurring failure classes here (skipped-test-as-pass, cross-environment benchmark, self-review as "security reviewed", unlabeled default changes) should be seeded into the project's registry or PR template checklist. I recommend adding them to the PR template; if that is declined, note it so the absence is on record.
