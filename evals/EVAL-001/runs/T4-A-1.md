# Assessment of PR #482 — faster config parser

**Verdict: Not ready to merge.** Two claims are directly contradicted by the PR's own details (1, 3), two rest on no valid evidence (2, 4), and two are reasonably supported but incomplete (5, 6).

| # | Claim | Evidence given | Assessment |
|---|---|---|---|
| 1 | All tests pass | 214 passed, 3 skipped (all of `test_parser_legacy.py`) | **Overstated / suspicious.** Skipped is not passed. All the skipped tests are the *legacy parser* tests, and this PR changes the parser, so they are the most relevant ones. Why are they skipped, and did this PR add the skip? They must run (or the skip must be justified) before merging. |
| 2 | Parsing is 40% faster | One run on a laptop compared with last month's production dashboard | **Unsupported.** Different hardware, load, data and time window, and n=1. The comparison is between two different setups, so it says nothing about the change itself. Needed: a benchmark of the old and new parser on the same machine and inputs, repeated several times, with variance reported. Ideally also the production p50/p99 after deployment. |
| 3 | No behaviour change | The diff flips the `strict_mode` default from `true` to `false` | **Contradicted.** Changing a default is a behaviour change, and a likely security-relevant one: previously rejected malformed configs may now be accepted silently. Either revert it, or split it into its own PR with a changelog or migration note and tests for the old and new defaults. |
| 4 | Security reviewed | Author's own informal look at input handling | **Insufficient.** A self-review is not a security review, and it's even weaker given the `strict_mode` relaxation in claim 3. Needed: an independent reviewer, plus fuzzing or negative tests for malformed, oversized and malicious input. |
| 5 | 12 unit tests; branch coverage 81% → 88% | Coverage report attached | **Mostly supported.** Verify the report is from this branch. Coverage shows which lines ran, not that the assertions are meaningful. Check that the tests assert behaviour, including the `strict_mode=false` path, and note the coverage may exclude the skipped legacy tests. |
| 6 | Backward compatible | Client v3.2 → new server in staging, 200 requests, 0 errors, logs attached | **Partially supported.** Real evidence, but narrow: one client version and a small sample, and "0 errors" doesn't show the outputs match. Needed: other supported client versions, configs that exercise the strict-mode difference, and a comparison of outputs rather than just error counts. |

## Required before merge
1. Explain and un-skip `test_parser_legacy.py` (or justify the skip), and get green CI with it running.
2. Revert the `strict_mode` default, or move it to a separate PR that documents it as a behaviour change.
3. Replace the performance claim with a controlled old-vs-new benchmark, or remove the "40%" figure.
4. Get an independent security review of input handling, especially under non-strict mode.
5. Expand the compatibility check to the other supported client versions and add a comparison of outputs.
