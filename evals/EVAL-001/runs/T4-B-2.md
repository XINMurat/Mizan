# Mizan Audit: PR #482 "faster config parser"

**HARKing status:** This is a retrospective audit of claims the author wrote after seeing the results. No thresholds were locked in advance, and that includes the thresholds used here. **Coverage:** 6 of 6 claims audited, using only the PR text. I did not open the diff, CI logs, coverage report or staging logs, so every tier below is capped by that. **Constraint:** the audit had one read and one write, with no access to the repository.

**Verdict: Do not merge as-is.** No claim reaches `[K]` on the evidence given. Two claims are contradicted by the author's own parentheticals (1, 3). One is measured against the wrong baseline (2). One is self-arbitrated (4).

## Conjunction audit (step 8): the pairs that matter

| Feature | Guarantee it can reach | Outcome |
|---|---|---|
| `strict_mode` default → false | Security of input handling (claim 4) | **Unchecked. This is the highest-risk pair.** Strict mode is usually the input-validation guarantee. The security review does not mention the change. |
| `strict_mode` default → false | Backward-compat evidence (claim 6) | **Confounded.** Laxer parsing makes "0 errors" easier to get and less informative. |
| `strict_mode` default → false | Performance (claim 2) | **Confounded.** Skipping validation may be where the "40%" comes from, rather than the new parser. |
| Legacy tests skipped | "All tests pass" (1) and coverage delta (5) | Both claims describe a suite that has the relevant tests removed. |

The core finding: **one undisclosed-as-such change (`strict_mode`) is a plausible single explanation for the speedup, the zero errors, and the risk the security review did not examine.**

## Missing card (step 6)

The PR format shows only successes. It cannot show why the legacy tests were skipped, what inputs `strict_mode=true` used to reject, the variance of the benchmark, or who other than the author looked at the code.

## Next steps (ordered by criticality × impact/effort)

1. **Split or justify the `strict_mode` flip.** Recommendation: revert it in this PR and propose it separately with its own rationale. If it's wrong to keep it here, you get a silent security and behaviour regression in production. Reverting costs one line.
2. **Un-skip `test_parser_legacy.py`** or document why each test is skipped. Then re-run CI. Recommendation: make this a merge blocker. It's cheap to do, and those tests are the most relevant ones for this PR.
3. **Independent security review** of the input handling, with strict mode on and off. The arbiter must be `third_party`.
4. **Re-benchmark properly:** old and new parser on the same machine with the same inputs, at least 30 runs each, with medians and a CI. Also run the new parser with `strict_mode=true` to separate the parser gains from the gains of skipping validation. Preregister the claim as: median parse time drops by ≥20% and the 95% CI excludes 0.
5. **Broaden the compat test:** use every supported client version, the current `strict_mode` default, and a replay of real production configs, including ones that strict mode used to reject.
6. Edit the PR description: change "all tests pass" to "214 passed, 3 skipped (legacy)" and change "no behaviour change" to name the default change.

## Registry seed (surviving `[H]` claims)

- **H-482-1** The new parser is faster. Arbiter: `runtime` benchmark on the same machine. Threshold: median ≥20% faster, CI excludes 0, n ≥ 30 per arm, `strict_mode` held constant. Exclusion rule: first 3 warm-up runs. Refutation: CI includes 0. Rival hypothesis: the gain comes from skipping strict validation.
- **H-482-2** Backward compatible for all supported clients. Arbiter: `runtime` staging replay. Threshold: 0 errors and identical parse output on ≥1000 replayed production configs per client version. Refutation: any divergence in parse output.
- **H-482-3** The new branches are covered by meaningful tests. Arbiter: `instrument` (mutation testing). Threshold: mutation score ≥70% on new branches.
