# Assessment of PR #482 — faster config parser

**Verdict: Not ready to merge.** One claim is contradicted by the PR itself (#3). Two are unsupported (#2, #4). One is overstated (#1). Two are reasonably supported but narrow (#5, #6).

| # | Claim | Evidence given | Status |
|---|-------|----------------|--------|
| 1 | All tests pass | CI: 214 passed, 3 skipped (all in `test_parser_legacy.py`) | **Overstated** |
| 2 | 40% faster | One run on a laptop, compared with last month's production dashboard | **Unsupported** |
| 3 | No behaviour change | The diff flips the `strict_mode` default from `true` to `false` | **Contradicted** |
| 4 | Security reviewed | The author reviewed their own code informally | **Unsupported** |
| 5 | 12 new tests, branch coverage 81% → 88% | Coverage report attached | **Mostly supported** |
| 6 | Backward compatible | Client v3.2 in staging, 200 requests, 0 errors, logs attached | **Partially supported** |

## 1. "All tests pass": overstated
214 tests passed, but 3 were skipped. "All tests pass" is only true if those 3 don't count. The skipped tests are the legacy-parser tests, and a parser rewrite is exactly what they would check. Given claims #3 and #6, those are the tests that matter most here.
**Needed:** say why they are skipped (skipped before this PR, or skipped by this PR?). Run them, or delete them with a stated reason. Restate the claim as "214 passed, 3 skipped because…".

## 2. "40% faster": unsupported
- It is one measurement, so there is no variance and no way to tell a real change from noise.
- It compares two different things: a laptop run against production dashboard numbers. Hardware, load, input data, network, and the time period all differ. The 40% can't be attributed to the code change.
- It doesn't say which metric (p50? p99? mean?) or which workload.
**Needed:** a benchmark comparing the old and new parser on the same machine, with the same inputs and repeated runs. Report the median and spread (or a CI), plus the benchmark script. Ideally, also check this against production after deploy.

## 3. "No behaviour change": contradicted
The PR says the diff changes the `strict_mode` default from `true` to `false`. That is a behaviour change by definition, and possibly a security or data-validation one: inputs that used to be rejected may now be accepted silently. It also weakens claims #4 and #6, since neither says it tested with the new default in mind.
**Needed:** revert the default change, or move it into its own PR with a changelog or migration note. Then retract the "no behaviour change" claim and explain which callers depend on strict mode.

## 4. "Security reviewed": unsupported
A self-review by the author is not a security review. Nothing is recorded: no reviewer, no checklist, no fuzzing, no threat model. Relaxing strict mode (#3) is a change to input validation, the most security-relevant thing in a parser, and the review statement doesn't mention it.
**Needed:** an independent reviewer who is told about the `strict_mode` change. Add tests for malformed or hostile input (fuzzing if possible) under both modes.

## 5. New tests and coverage: mostly supported
The attached report is real evidence, and the increase is plausible. Caveats:
- Coverage shows lines were run, not that the assertions are good.
- Do any of the 12 tests use `strict_mode=false`, now the default? Are both modes tested?
- The 3 skipped legacy tests mean some old behaviour is not covered at all.
**Needed:** a quick look at what the tests assert. Confirm that both `strict_mode` values are tested.

## 6. Backward compatible: partially supported
This is the best-evidenced claim: a real client, a real server, and logs attached. But:
- It covers one client version (v3.2). Other supported versions weren't tested.
- 200 requests is a small sample. Which config shapes did they use? Edge cases and legacy formats may not have been covered.
- "0 errors" under a looser default proves little. With `strict_mode=false`, bad input may now succeed silently instead of erroring. Zero errors could hide a change in behaviour, not prove compatibility. Responses should be compared with the old server's, not just checked for errors.
**Needed:** list the supported client versions and test them all. Replay representative production configs and diff the parsed output between old and new.

## What must happen before merge
1. Resolve the `strict_mode` default change: revert it or split it out. Correct claim #3.
2. Replace the performance claim with a proper old-vs-new benchmark, or drop the number.
3. Account for the 3 skipped legacy tests.
4. Get an independent security review that covers the relaxed validation.
5. Strengthen the compatibility evidence with an output diff and all supported client versions.
