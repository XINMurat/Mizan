# Review of PR #482 — faster config parser

**Verdict: do not merge yet.** Two claims are contradicted by the PR itself (1 and 3). Two are unsupported (2 and 4). One is partly supported (5). One is reasonably supported but narrow (6).

## 1. "All tests pass" — misleading
- **Evidence:** CI shows 214 passed and 3 skipped.
- **Problem:** The skipped tests are exactly the ones in `test_parser_legacy.py`. Those are the tests most likely to catch a regression in a parser rewrite. A skipped test didn't pass; it wasn't run. So "all tests pass" says more than the evidence shows.
- **Questions:** Why are they skipped? Were they skipped before this PR, or does this PR add the skip? Was the skip added because they fail?
- **Required:** Run those 3 tests or give a documented reason they don't apply. Then say accurately "214/217 pass, 3 skipped because X".

## 2. "Parsing is 40% faster" — not supported
- **n = 1:** It's a single measurement with no variance, no repeats and no warm-up control.
- **Invalid baseline:** A laptop run is compared with last month's production dashboard latency. Hardware, load, input configs and time period all differ. Dashboard latency also likely covers more than parsing (I/O, network, the rest of the request).
- **No control:** The old parser was never run under the same conditions.
- **Required:** A benchmark of old vs new on the same machine, with the same inputs (including realistic or large configs), over many iterations, reporting the median/p95 and spread. Until then, the most the author can say is "possibly faster".

## 3. "No behaviour change" — contradicted by the diff
- The diff changes the default of `strict_mode` from `true` to `false`, and that is a behaviour change by definition. Configs that used to be rejected (malformed, unknown keys and so on) may now be accepted silently. That can hide errors, and it can have security consequences.
- **Required:** Either revert the default or split it into its own PR with its own justification, a changelog entry and a migration note. Also add tests that pin the strict and non-strict behaviour.

## 4. "Security reviewed" — not supported
- It's a self-review by the author, with no checklist, no named threats, no tooling (fuzzing, SAST) and no independent reviewer. The only finding is "looks fine".
- A new parser is exactly the kind of input-handling surface that needs real review. The `strict_mode` relaxation in claim 3 makes this more pressing, because more lenient parsing widens what input is accepted.
- **Required:** An independent reviewer, ideally with fuzzing or malformed-input tests (deep nesting, huge inputs, injection in values, encoding edge cases).

## 5. "12 unit tests, branch coverage 81% → 88%" — partly supported
- **Supported:** There is an attached artifact (the coverage report) with a before/after number. That is the best-evidenced claim here.
- **Limits:**
  - Coverage measures which code ran, not whether it behaves correctly. Tests without strong assertions can raise coverage without checking anything.
  - Were the before and after numbers measured on the same suite configuration? The 3 legacy tests are skipped, and that may change the baseline.
  - "Covering the new parser branches" should say which branches are still uncovered. That's the remaining 12%, including error paths.
- Reviewers should read the 12 tests for their assertion quality.

## 6. "Backward compatible: client v3.2, 200 requests, 0 errors" — reasonably supported, but narrow
- **Supported:** It's an actual test in staging with a stated sample size and attached logs, so it can be checked.
- **Limits:**
  - Only one client version was tested. Are older supported clients (v3.0, v3.1, v2.x) in scope?
  - 200 requests may not exercise edge-case configs. Were they varied, or the same request repeated?
  - "0 errors" catches crashes but not silent semantic differences. With `strict_mode` now false, bad input could be accepted without any error. A differential test (old vs new parser output on the same inputs) would give much stronger evidence of compatibility.
- The claim holds for "client v3.2 under this traffic sample". It doesn't establish backward compatibility in general.

## Summary

| # | Claim | Status |
|---|-------|--------|
| 1 | All tests pass | Overstated: the 3 relevant legacy tests are skipped |
| 2 | 40% faster | Unsupported: n=1 and a mismatched baseline |
| 3 | No behaviour change | False: the `strict_mode` default flipped |
| 4 | Security reviewed | Unsupported: self-review only |
| 5 | Tests + coverage | Partly supported: coverage is not correctness |
| 6 | Backward compatible | Supported for v3.2 only; narrow scope |

**Before merge:**
- Resolve the skipped legacy tests.
- Revert the `strict_mode` default or split it into a separate PR.
- Run a proper A/B benchmark, or drop the performance claim.
- Get an independent security review.
- Add a differential old-vs-new parser test.
