## Claim-by-claim

**1. Paged at 14:05.** `[H]` Makul Hipotez / Plausible hypothesis
Unsourced. It is checkable against pager logs. Survives as a plausible timestamp.
*Next step:* Attach the pager log entry. Name the alert or source that triggered the page, since it determines whether the new alert adds any value (see claim 7).

**2. Outage lasted 47 minutes, 14:03 to 14:52.** `[R]` Reddedildi / Refuted (as stated)
14:03 to 14:52 is 49 minutes. The stated duration does not match its own endpoints. The likely mechanism: 14:05 to 14:52 is exactly 47 minutes, so the duration may have been measured from the page time, not from onset. If so, the paging delay is hidden inside the headline number and the 14:03 start is wrong, or the duration is wrong. Either way the figure cannot be published as written.
*Next step:* Pull the first error-rate sample above baseline from the load balancer logs. Use that as onset, recompute the duration, and state the method.

**3. Error rate peaked at 38% (load balancer logs).** `[K]` Kanıtlanmış / Proven (provisional)
A source is cited and the metric is specific. I have not seen the logs.
*Next step:* Attach the log query and the window used. State whether 38% is per-minute peak or over a longer window.

**4. Root cause: cache eviction change in release 8.2. Rolled back at 14:50; errors stopped shortly after.** `[KKE]` Kritik Kontrol Eksik / Critical control missing
This is the main finding, and the evidence does not support it yet.

- The DNS provider's incident resolved at 14:49 (claim 6). That is one minute before the rollback. Recovery is confounded: the errors could have stopped because DNS recovered, not because of the rollback.
- "Shortly after" has no timestamp, so the postmortem cannot say which event came first relative to the error drop.
- The deploy time of 8.2 is not stated. If 8.2 went out before 14:03, the timing supports the cache hypothesis. If it went out well before, the cache change had to be fine for a long time before failing, which needs explaining.
- Nothing shows the errors were caused by cache eviction. A rollback followed by recovery is a temporal correlation.

The symmetric control is missing. The postmortem needs one of:

- Error-rate series at 1-minute resolution, split by failure type (DNS resolution errors vs. cache-path errors vs. other). If the DNS-related errors cleared at 14:49 and cache-related errors persisted until 14:50, the cache story gains support. If they cleared together, the confound stands.
- Reproduction in staging: 8.2 with DNS healthy and DNS failure injected, and 8.1 under the same DNS failure. Either result would discriminate.

Until one of these runs, the root cause is a hypothesis, not a finding.
*Next step:* Add the deploy timestamp, the per-minute error series, and the error-type breakdown. Reword the root cause as "suspected" with the DNS confound listed. Register the cache hypothesis with a refutation condition (see Next steps below).

**5. No customer data was affected; checked the three services we suspected might have written partial orders.** `[Y]` Yanıltıcı / Misleading
The claim is worded as a system-wide result. The check covered three services selected by suspicion. A result scoped to three services cannot support "no customer data was affected." The check also covers writes only. A cache eviction fault can serve stale or wrong data to customers without writing anything, and that path is not addressed.
*Next step:* Reword to the scope actually checked. Then check every service on the checkout path, including cache-served reads. Reconcile payment-provider records for duplicate or failed charges during 14:03 to 14:52. Only then can a data-impact statement be made.

**6. Upstream DNS provider's status page records an incident, resolved at 14:49.** `[K]` Kanıtlanmış / Proven (for the fact only)
The external record is cited and the timestamp is specific. The postmortem never says whether this incident affected our service. Stating the provider's incident exists does not establish causation.
*Next step:* Show whether our resolution failures or upstream timeouts began at 14:03 and ended around 14:49. Name the DNS dependency explicitly, since the document never does.

**7. Alert (error rate above 5% for 2 min) would have fired at 14:06 in replay.** `[KKE]` Kritik Kontrol Eksik / Critical control missing
Three problems:

- **Threshold lock violated.** The 5%/2-minute rule was chosen after seeing this incident, then replayed on the same incident. That is HARKing. A held-out replay is required. The threshold must be fixed before evaluating it on a new incident.
- **No false-positive baseline.** The alert has not been checked against normal traffic. A 5% threshold on a checkout system may fire routinely on a bad minute.
- **No lead time in this incident.** The alert would fire at 14:06, one minute after the 14:05 page. In this incident it would have added nothing. The postmortem presents it as an improvement without saying so.

*Next step:* Run the alert against a set of normal-traffic days to measure false positives. Evaluate it on incidents not used to design it. Report the lead time over the existing paging path, which is the value that matters.

**8. This will not happen again.** `[S]` Spekülatif / Speculative
Not testable as written. No refutation condition, no timeframe, no metric. It cannot be checked and it cannot fail, so it is decoration.
*Next step:* Replace it with a falsifiable claim, for example: "A checkout error-rate event above 5% for 2 minutes caused by a cache-eviction change will be detected within 3 minutes and rolled back within 15 minutes, measured over the next 90 days." Register it with a review date.

**9. The team held a retrospective on Friday.** `[H]` Makul Hipotez / Plausible hypothesis
Unsourced and undated. 2026-09-18 is a Friday, so "Friday" may mean the same day as the incident or the following Friday. If it was the same day, the retrospective could not have had the full data described above. This does not affect the technical claims, but the date should be stated.
*Next step:* Add the retrospective date and attendee list.
