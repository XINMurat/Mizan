# Mizan Audit: Checkout Outage Postmortem, 2026-09-18

**HARKing status:** Retrospective. The postmortem was written after the outcome was known, and its alert threshold was almost certainly chosen after seeing this incident. This audit is also retrospective and was done from the text alone.

**Coverage:** 13 atomic claims extracted from 9 items. None of the sources (LB logs, deploy records, DNS status page, alert config) were attached, so nothing was verified against primary data. One claim (the duration arithmetic) is checkable from the text itself.

**Verdict:** Only the timeline and impact description is usable as drafted. The root-cause claim is not supported yet, and two conclusions (item 5 and item 8) say more than the evidence allows.

## Failures in detail

**Item 2 (arithmetic, [R]).** The stated duration is 49 minutes, not 47. One of the three numbers is wrong, and the error should be fixed before publication. The mismatch matters because the duration anchors the impact estimate. If the start was 14:05, that also explains the page time, and that would change the story (see below).

**Item 4 (root cause, [KKE]).** Three things could flip this claim and none has been run:
- **Recovery confound.** The DNS incident resolved at 14:49. The rollback happened at 14:50. Errors stopped "shortly after" 14:50. The recovery is equally consistent with the DNS fix and the rollback, and the document does not separate them.
- **Onset not shown.** The document gives no 8.2 deploy time. If the DNS incident began before 14:03, the onset is explained without 8.2.
- **No mechanism.** Nothing explains how cache eviction produces a 38% error rate.

*Recommendation:* Pull the 8.2 deploy timestamp and the DNS incident start time. If the deploy precedes 14:03 and the DNS incident started after it, root cause stands at [H] pending a reproduction. If the DNS incident started earlier, the root cause is "shared or undetermined" until a controlled test is run. Cost if I'm wrong: the team fixes the cache code and the DNS dependency stays unguarded.

**Item 7 (alert, [KKE]).** Two problems.
- **No lead time.** The page happened at 14:05 and the new alert would fire at 14:06. In this incident the new alert would have been one minute later than the existing page. The document presents it as an improvement without showing one.
- **In-sample tuning.** A 5%/2-minute threshold replayed on the same incident that suggested it proves nothing about other incidents. It needs a held-out window of normal traffic to measure false positives.

*Recommendation:* Replay against 30 or more days of normal traffic to get a false-positive rate, and state the threshold as preregistered for future incidents.

**Item 5 ([Y]).** "No customer data was affected" is a claim about data integrity, but the checked scope was three services suspected of writing partial orders. The postmortem does not state how many services write orders, which of those were excluded, or what check was run. The wording should become: "Three services suspected of writing partial orders were checked; no partial orders were found. Checks on the remaining writers: [pending / list]."

**Item 8 ([Y]).** "This will not happen again" is a prediction with no refutation condition. Replace it with a testable commitment, for example: "The 8.2 eviction path is covered by a load test at 40% error injection before release; the DNS dependency has a fallback or circuit breaker, status: [owner, date]."

## The missing card

A postmortem template cannot show:
- **Customer impact.** A 47-minute checkout outage at 38% errors means failed orders and payments. The document reports no count. "No customer data affected" answers a different question.
- **The detection gap.** Between onset (14:03) and page (14:05), what detected the problem? That gap is what the new alert is supposed to close.
- **Rival hypotheses.** The DNS incident appears in the timeline and nowhere in the analysis.
- **Action-item status.** No owners, no dates, no closure criteria.
- **Duplicate or orphaned writes.** Clients retrying during a 38% error rate can create duplicate orders. This is the conjunction below.

## Conjunction check (domain probe pending)

- **Eviction change × order writes.** Under elevated errors, retries plus non-idempotent writes can produce duplicate or partial orders. Status: **unchecked.** Item 5 covers three writers only, and the document does not say whether retries were idempotent.
- **New alert × DNS failure.** An error-rate alert fires for any cause, so it tells you something is wrong but not which dependency. Status: **unchecked**, and it matters for item 8's claim that the response is adequate.
