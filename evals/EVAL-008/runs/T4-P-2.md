## Errors, located

**Claim 2, duration.** 14:03 to 14:52 is 49 minutes. Either the start, the end, or the duration is wrong. The impact is small in size but large in trust: it's the first number a reader checks. Fix it and find out which endpoint is wrong, because that changes the timeline.

**Claim 4, root cause.** The mechanism of error is the rollback causing recovery. The confound is the DNS incident. Both changes landed within about a minute of each other: DNS resolved at 14:49, rollback at 14:50. The postmortem cannot distinguish them. Two further gaps:
- The deploy time of 8.2 is not stated. If 8.2 shipped hours before 14:03, it does not explain onset at 14:03.
- "Errors stopped shortly after" is unquantified. If errors stopped at 14:50 or 14:51, that is evidence for the rollback. If they dropped only after 14:52, it is not.

**Claim 7, alert.** Three problems:
- **Post-hoc tuning.** The 5%/2-min threshold was apparently chosen with this incident's logs in view. A replay against the same incident can only confirm the threshold was fit to it. Record the threshold as set after the event, not as validated.
- **No false-positive baseline.** Nothing shows how often 5%/2-min fires on normal days. An alert that fires on a bad deploy and on random noise is a different thing from one that fires only on incidents.
- **It would have been late.** A human was paged at 14:05. The new alert replays to 14:06. Against the actual incident, the alert adds nothing and is one minute slower than the page. The postmortem presents this as an improvement without saying so.

**Claim 5, data impact.** "No customer data was affected" is a universal statement backed by a check of three suspected services. If partial-order writes could have occurred elsewhere, the claim is unsupported. The supportable version: "In the three services checked for partial order writes, none were found."

**Claim 8.** Not a finding. It is a commitment with no mechanism, no metric, and no way to be wrong.

## Survivors

- Claim 6, as a fact, survives: the provider recorded an incident resolved at 14:49. Its relevance to your outage is what's unresolved.
- Claim 1 is plausible and consistent with a 14:03 onset, but needs the pager record.

## Next steps

2. **Run the DNS control.** Check your resolver and dependency logs for failures during 14:03 to 14:52, and whether your traffic used the affected resolvers. Then ask: if DNS had been the only cause, would the rollback have changed anything? Record the answer in the postmortem.
3. **Establish the mechanism for the root cause.** Reproduce the cache eviction failure against release 8.2 in staging, or cite the code path that produces partial failures at the observed rate. Until then, the root cause is `[H]`, not "root cause."
4. **Rewrite the alert entry as a preregistration.** Set the threshold now, then run it on the last N non-incident days to measure false positives. Report the replay on this incident as the one case it was tuned on, not as validation.
5. **Rescope the data claim.** Either run the write audit across every service that can write orders, or narrow the sentence to what was checked.
6. **Replace claim 8** with a falsifiable one, for example: "A test reproducing the 8.2 eviction failure runs in CI, and the alert in item 4 fires within 2 minutes on a replay of the incident with fewer than X false positives across N normal days." Each part can then be checked.
